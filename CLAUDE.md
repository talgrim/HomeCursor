## Project

HomeCursor lets a phone control a PC's mouse and keyboard over the local network (no cloud, no accounts). Two parts: a **C# host** (Windows, in `src/host`) and a **Kotlin Android client** (Jetpack Compose, in `src/client`). The project is in early development: the host receives client messages and injects input (no pairing or encryption, by design: the host serves one client at a time on a trusted LAN), while the client can discover and connect to a host, remembers it and works as a touchpad (move, click, right click, middle click, scroll, drag) and keyboard (portrait: list of shortcuts; landscape: full-screen on-screen keyboard).

## Commands

All host commands run from `src/host` (solution: `HomeCursor.Host.sln`, .NET 9).

```bash
dotnet build HomeCursor.Host.sln
dotnet test HomeCursor.Host.sln
dotnet test --filter "FullyQualifiedName~HostServiceTests.StopAsync_AfterStart_SetsStopped"   # single test
dotnet run --project HomeCursor.Host.Tray    # Windows only
```

There is no lint step configured.

The client is a Gradle project in `src/client` (AGP 9 with built-in Kotlin, version catalog in `gradle/libs.versions.toml`). From that directory: `./gradlew assembleDebug` to build, `./gradlew test` for unit tests. It needs a JDK and the Android SDK (`local.properties` with `sdk.dir` is gitignored). There is no Linux JDK in WSL; on this machine build via Windows using Android Studio's bundled JBR as `JAVA_HOME`, e.g. `cmd.exe /c gradlew.bat assembleDebug`.

## Architecture

- `HomeCursor.Protocol` is the wire protocol (messages, binary codec, TCP framing, UDP and discovery packets). It has no dependencies. The language-neutral spec is `docs/protocol.md`; keep it in sync when changing the protocol.
- `HomeCursor.Core` holds all host logic behind abstractions (`IHostService` and friends). It is UI-agnostic and must not reference WinForms. `HostService` runs `IHostLoop`s (`TcpControlListener`, `UdpPointerReceiver`, `DiscoveryBeacon`, all derived from `HostLoopBase`); `ISessionGate` lets only the first client connect and `ISessionMonitor` (same `SessionGate` instance) exposes the current client plus `SessionStarted`/`SessionEnded` events (with a `SessionEndReason`) to the UI; `IMessageDispatcher` turns messages into `IInputInjector` calls; settings come from `ISettingsProvider` (`JsonFileSettingsProvider`, `settings.json` next to the executable, shipped from `src/host/HomeCursor.Host.Tray/settings.json`). Dependencies are wired with `Microsoft.Extensions.DependencyInjection`: `AddHomeCursorCore()` (Core) registers the gate, dispatcher, loops (registration order = start order) and `IHostService`; the Tray project (composition root, `Program.cs`) adds logging, `ISettingsProvider`, `IInputInjector` and `TrayApplicationContext`. Loops read settings via `IOptions<HostSettings>`. Logging uses `Microsoft.Extensions.Logging` abstractions only.
- `HomeCursor.Host.Windows` implements `IInputInjector` with `SendInput`.
- `HomeCursor.Host.Tray` is a thin tray-only WinForms shell (`ApplicationContext` + `NotifyIcon`, no main window). It shows the connected client (menu item, tooltip, generated idle/connected icons) and balloon notifications on connect/disconnect (settings `NotifyOnClientConnection` and `NotifyOnClientDisconnection`), marshalling events to the UI thread. It composes the host in `Program.cs`, adds the Debug logger and only depends on Core abstractions, so Core can later be driven from a console app or tests. It is a normal user process on purpose: input injection must happen in the logged-in user's session, so a Windows Service (Session 0) is not suitable.
- `HomeCursor.Protocol.Tests` and `HomeCursor.Core.Tests` are xUnit. Network tests use loopback sockets on free ports and hand-written fakes (no mocking library).
- The Android client (`src/client/app/src/main/kotlin/com/homecursor/client`) is layered so everything except `ui` and the small Android classes (`MainActivity`, `SharedPrefsSavedHostStore`, `SharedPrefsTrackpadSettingsStore`) is plain Kotlin, testable on the JVM: `protocol` (Kotlin port of the wire protocol, including the pointer, Key and Text messages and the UDP pointer packet), `discovery` (`UdpHostDiscovery`: UDP broadcast probe, collects replies), `connection` (`TcpHostConnector`/`HostSession`: Hello/Welcome handshake, ping loop, dead-host detection; `HostSession.send` is the only TCP write path), `input` (the trackpad logic, see below), `storage` (`SavedHostStore`: last host; `TrackpadSettingsStore`: pointer sensitivity and scroll direction, in a prefs file of its own because forgetting the PC clears the saved-host file), `session` (`ConnectionCoordinator`: connect to the saved host, find it again by name if its address changed, retry while the host answers Busy, reconnect after a lost connection; exposes `inputSender`, a sender for the live connection or a no-op one), `ui` (`HomeViewModel`, `TrackpadViewModel`, Compose with `TrackpadScreen` as the connected screen). The connection lives only while the app is in the foreground: `MainActivity` calls `onForeground` in `onStart` and in `onStop` (except when `isChangingConfigurations`) first lets `TrackpadViewModel` release held buttons, then closes the connection cleanly, so the host frees its single client slot at once.
- Trackpad flow (client): the UI reports every finger that is down on each touch event to `TrackpadViewModel`, which feeds `TrackpadGestureInterpreter` (a pure state machine: touch frames in, `PadCommand`s out: move, scroll, click, button down/up). Move and scroll motion goes through `PointerAcceleration` and sensitivity into `MotionAccumulator`s (fractions carry over, Int16 clamp) and is sent at most every 8 ms; a click or button change first sends the pending motion. `TcpUdpInputSender` queues input and delivers it in order: move and scroll as UDP datagrams, buttons, keys and text over TCP. All pixel and time constants live in `TrackpadTuning` (defined in dp, converted with the screen density). Gestures: one finger moves, tap is a left click, two-finger tap is a right click, two-finger drag scrolls, tap then touch-and-move drags with the left button held. A third finger ends the gesture until all fingers are lifted. A one-finger tap's click is held back (`hasPendingClick`) for the double-tap window, so that a drag after it is one button press and not a second press at the same spot, which Windows takes for a double click; `TrackpadViewModel` runs a timer that calls `flushPendingClick()` when no touch came, and a new touch settles the click itself. `TrackpadTuning.pointerSpeedScale` (0.5) is multiplied with the sensitivity setting, so the setting reads 1× at a comfortable speed.
- Keyboard flow (client): the keyboard button (an icon) in `TrackpadScreen`'s button strip (Left, Mid, Right, each drawn as a mouse with its zone filled by `MouseGlyph`, and a small tonal keyboard button; Mid is a hold button like Left and Right, there is no gesture for the middle button; the strip is at the bottom in portrait and on the left in landscape; the settings gear is overlaid on the pad's upper right corner and a connection chip with the host name on its upper left corner, in both) leads, via `ConnectedScreen`, to `ShortcutsSheet` in portrait (`ShortcutsViewModel`: list of `Shortcut`s, seeded from `DefaultShortcuts`, saved by `SharedPrefsShortcutStore` as one string through `ShortcutSerializer`; tap runs a shortcut, "Edit" manages it) and to the full-screen `KeyboardScreen` in landscape (`KeyboardViewModel`: sticky modifiers, `KeyboardMode.RealTime` sends Key messages, `KeyboardMode.Compose` types into a field and sends the whole text as Text messages, split by `TextChunker`). Opening the keyboard sets `requestedOrientation` to sensor-landscape in `MainActivity` (it follows `KeyboardViewModel.isOpen`); closing it, or the app leaving the foreground, releases held modifiers. `SpecialKey` carries physical keys (letters, digits, punctuation as Windows virtual keys on a US layout) so shortcuts like Ctrl+C work; text in other languages goes through Text.
- Tutorial (client): `TutorialViewModel` runs a step-by-step tour (`TutorialSteps`, strings `tutorial_*`) over the trackpad: `ConnectedScreen` calls `onTrackpadShown()`, which starts it once (`TutorialStore`, `SharedPrefsTutorialStore`, a prefs file of its own so "Forget this PC" does not reset it), and the Tutorial item in the settings sheet starts it again. `TrackpadScreen` marks the pad, buttons, keyboard button and gear with `tutorialTarget`, and `TutorialOverlay` (a full-screen dialog) dims the screen around the current target. A new gesture or button needs a step in `TutorialSteps`.
- Theming (client): `ui/theme/` holds `HomeCursorTheme` (brand palette in `Color.kt`, light and dark, following the system dark mode with no in-app toggle; type, shapes and the `Spacing` scale). Use `MaterialTheme.colorScheme`/`shapes` and `Spacing` instead of colour or `.dp` literals. `MainActivity` is edge-to-edge and the window background comes from `res/values(-night)/themes.xml`. Composables have light and dark `@Preview`s.
- Tests use hand-written fakes and loopback sockets, no mocking library. The Compose layer has no automated tests; check it on a device.

## Environment notes

- Development happens partly under WSL. `dotnet new winforms` fails on Linux, and the Tray project builds there only because its csproj sets `EnableWindowsTargeting`. Building works on WSL, but running the tray app requires Windows, so verify tray behavior on Windows.
- Git on this checkout converts LF to CRLF (`core.autocrlf`); `.gitattributes` keeps LF in the repository.
